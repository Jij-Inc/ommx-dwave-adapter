# Adapter conversion benchmark results

2026年8月25日実施のOMMX v2/v3ローカル測定結果です。

## 結論

- v3の通常benchmarkは一律なデグレではありません。ウォーム後時間の中央値は、Instance → Modelで0.9%増、Result → Solutionで2.0%増です。
- v3のResult → Solutionのピークメモリは全36ケースで改善し、1.8%〜28.4%減でした。一方、Instance → Modelのメモリ中央値は38.0%増で、Instance種別とallocator境界によるばらつきがあります。
- native OneHotのInstance → Modelはv2比で時間38.0%〜63.7%増、メモリ104.8%〜154.1%増でした。ただし通常制約版でも時間9.0%〜31.1%増、メモリ121.0%〜173.8%増であり、native OneHot固有だけでなくv3の変換経路全体の差を含みます。
- v3 preparedとv3 directは同一CQMです。Preparation履歴によるInstance → Model時間差は-1.4%〜3.9%で、時間上の明確なデグレは見られません。
- Preparation履歴はInstance → Modelメモリを7.5%〜21.9%、Result → Solution時間を5.5%〜19.6%、同メモリを12.2%〜28.8%増加させました。decodeではremoved制約の評価コストを含みます。
- prepare単体は0.093〜0.994 ms、13.859〜109.289 KiBでした。

## 測定条件

- 時間：ms。ウォームアップ3回後、20回の中央値
- メモリ：KiB。memrayによる2回目のピーク
- 初回時間・初回メモリもCSVへ保存していますが、lazy initializationの影響が大きいため本文ではウォーム後を比較
- 比較率：`(比較対象 - baseline) / baseline`
- seed：0
- solver：未使用。決定的な実行可能解からdimod SampleSetをローカル生成
- SampleSet：各ケース1サンプル
- v2：OMMX 2.6.1 / dimod 0.12.20 / D-Wave System 1.29.1 / Adapter 0.1.2.dev6+g0769d65af.d20260825
- v3：OMMX 3.0.0b3 / dimod 0.12.20 / D-Wave System 1.29.1 / Adapter 0.1.2.dev26+g0728daf4d.d20260825
- 全414測定が成功（v2: 180、v3: 234）
- raw CSV：各branchの `benchmark_results/20260825-aligned/`（git管理外）
